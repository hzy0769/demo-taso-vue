# TASO 全球多语言与本地化设计方案

> 文档类型：产品 / UX / 内容 / 前端实施设计  
> 版本：v1.1（v1.0 方案 + §17 实现状态；v1.0 发布时未改动应用代码，实现状态见 §17）  
> 默认市场与界面：见 §17——原型已改为「设备建议冷启动」，无存档时不再写死香港  
> 适用范围：现有 Vue 原型的全部 61 个屏幕、弹层、提示和种子数据；后续 iOS、Android、Web 复用同一套规则。

---

## 1. 目标与边界

TASO 是全球美食、旅行、本地生活与会员权益产品。多语言设计不应只是把页面文案翻译成多份，而应让语言、内容、市场、时间、货币、地址与合规规则彼此独立、可组合。

本方案的目标如下：

1. 新安装、未登录、未保存过偏好的用户，默认看到**香港繁体中文**界面。
2. 用户可独立设置界面语言、内容语言、翻译目标语言、内容地区、时区和展示货币；任一项变化不应意外覆盖其他项。
3. 保留用户、商家、地点和原帖的原始语言与原始名称；翻译是可切换的呈现层，不是对原数据的覆盖。
4. 让金额、日期、地址、电话和法律/金融限制按正确的市场规则呈现，避免“翻译正确、业务含义错误”。
5. 支持先上线核心语言，后续扩展语言/市场时不重写页面结构或业务数据。

本期不包含翻译供应商选型、实时机器翻译成本、外部支付汇率、国家合规准入或后端 API 的实际建设。本文定义这些能力上线前必须满足的产品与数据契约。

## 2. 当前原型审计结论

原型已有全球化基础，但当前仍是“局部演示态”，不能支撑一致的多语言体验。

| 范围 | 已有能力 | 当前缺口 / 风险 | 设计结论 |
|---|---|---|---|
| 首次引导 | 欢迎页可选择语言、内容语言和地区 | 默认是“简体中文”；三个选择只是页面内 `ref`，不会写回账号或全局状态 | 以统一偏好模型驱动引导、登录前及登录后页面；新用户默认 `zh-Hant-HK` / `HK` |
| 设置 | 有“语言与地区”入口、内容语言、自动翻译和地区选择 | 显示为“简体中文 · HK”，选项不持久化；地区使用 Hong Kong / Tokyo 等城市名称混合表达 | 拆分界面语言、翻译语言、内容语言、内容地区、时区、展示货币 |
| 登录与账号 | 账号有 `countryCode`、`language`、`timezone` 字段 | 注册时国家固定 `HK`，界面语言却取 `navigator.language`；登录页主文案为英文、其余认证页中英混杂 | 以解析后的有效语言渲染所有认证界面；保留设备语言仅作建议，不覆盖默认或显式选择 |
| 社交内容 | 帖子含 `lang` / `original`，已可切换“翻译 / 原文” | 展示文案写死简体中文；原文与翻译字段方向不够明确；评论、聊天、搜索未建语言元数据 | 原文不可变，译文按目标语言作为派生资源；完整覆盖 UGC、搜索与语言反馈 |
| 国家地址 | 实体卡已按国家配置字段、邮编与电话规则 | 字段标签是中英硬编码；国家仅有 `zh` / `en` 两个名称；默认配送国是 JP；地址展示固定取中文名 | 地址配置和国家名称转为 locale catalog，默认国家改为 HK（仅新草稿） |
| 金额与日期 | 有会员卡 USD、实体卡 HKD、配送、流水等模型 | `fmt` 固定使用 `en-US`；金额符号和数值拼接在文案中；日期多为预格式化字符串或手工拼接 | 金额、日期、相对时间全部基于数据类型和 `Intl` / 平台 formatter；账本币种不因显示语言而改变 |
| 视觉与无障碍 | 基础字体和组件已统一 | 字体栈偏简体中文；按钮、标签和表格未预留英语扩张；`aria-label` 等辅助文案未纳入翻译 | 增加多脚本字体回退、长度预算、伪本地化和辅助技术验收 |

审计涉及的主要实现位置：`src/App.vue`（全局 Tab、对话框、Toast）、`src/screens/ScreenWelcome.vue`、`src/screens/ScreenLanguage.vue`、`src/screens/ScreenSettings.vue`、`src/store.ts`（账号、提示、数字格式）、`src/data.ts`（帖子/搜索/流水/社交种子数据）、`src/card.ts`（国家与地址）、`src/components/PostText.vue`（帖子翻译）和 `src/style.css`（字体与布局）。本次不修改这些文件。

## 3. 关键概念与解耦原则

以下字段不能互相推导后永久绑定。每个字段有独立来源、用户控制权和用途。

| 概念 | 示例 | 用途 | 用户是否可修改 |
|---|---|---|---|
| 界面语言 `uiLocale` | `zh-Hant-HK` | 导航、按钮、系统消息、表单、辅助文本 | 是 |
| 内容语言偏好 `contentLocales` | `['zh-Hant', 'en']` | Feed、搜索和通知的语言召回/排序信号 | 是，多选 |
| 翻译目标 `translationLocale` | `zh-Hant-HK` | 可翻译 UGC、商家摘要等的默认译文 | 是 |
| 内容地区 `contentRegion` | `HK` + `Hong Kong` | 本地 Feed、热点、商家与活动排序 | 是 |
| 账户国家/地区 `accountCountry` | `HK` | KYC、权益资格、可用支付方式等合规判断 | 受流程控制；不是普通语言设置 |
| 当前定位 `currentLocation` | 坐标或城市 | 附近内容、导航；仅在授权后使用 | 是，可随时关闭 |
| 公开所在地 `profileLocation` | `Tokyo` | 个人主页展示 | 是 |
| 时区 `timeZone` | `Asia/Hong_Kong` | 日期、相对时间、结算日和通知时间 | 是 |
| 展示货币 `displayCurrency` | `HKD` | 非账本的发现/价格比较场景；需说明汇率来源与时间 | 是 |
| 结算/原始货币 `transactionCurrency` | `USD`、`HKD`、`JPY` | 账本、支付、退款、卡费和交易凭证 | 否，由交易决定 |

特别规则：

- **界面语言不等于地区。** 在日本的香港用户可继续使用 `zh-Hant-HK`；香港的英文用户可使用 `en`。
- **内容地区不等于精确定位。** 用户选择“香港”可获得香港内容，但不表示公开位置或已授权定位。
- **显示货币不等于入账货币。** 现有 PRD 定义会员卡/钱包账本主要为 USD、实体卡办理费为 HKD。翻译或地区切换不能把交易实际币种改成 HKD，也不可在没有汇率、时间戳和免责声明时擅自换算。
- **语言标签使用 BCP 47；时区使用 IANA。** 不使用“繁體中文”“Hong Kong”这类显示字符串作为存储值。

## 4. 默认值、解析优先级与首次体验

### 4.1 全球默认配置

所有没有保存偏好、没有账号偏好且没有产品强制市场上下文的新会话，采用以下默认值：

```text
uiLocale             = zh-Hant-HK
translationLocale    = zh-Hant-HK
contentLocales       = [zh-Hant, en]
contentRegion        = HK / Hong Kong
timeZone             = Asia/Hong_Kong
displayCurrency      = HKD（仅限允许换算的发现/报价展示）
accountCountry       = 未确认；注册后或合规流程按用户资料确定
```

说明：香港繁体中文是产品默认界面，不代表每一位用户的账户国家，也不应把未确认的账户国家写死为 HK。对现有实体卡配送草稿，首次创建时默认收件国家为 HK；已填写或已保存的旧地址不得被自动覆盖。

### 4.2 生效优先级

同一字段按下列优先级解析，越靠前越优先：

1. 用户刚刚在当前会话中显式保存的偏好；
2. 已登录账号的已验证偏好；
3. 匿名用户本地保存的偏好；
4. 受渠道/活动明确约束的市场上下文（只影响被约束字段，并需可见说明）；
5. 产品全球默认值，即 `zh-Hant-HK` / 香港配置。

设备语言、系统时区、浏览器语言、IP 推断只可用于**“建议你使用…”**，不得在用户未确认时悄悄替换上述默认值，也不得覆盖已保存的选择。设备时区可作为首次设置的建议值，但默认仍为 `Asia/Hong_Kong`。

### 4.3 欢迎页交互

欢迎页首屏直接以繁体中文（香港）呈现，不弹出语言选择阻塞注册。页面提供一个紧凑的“語言與地區”入口，默认展开值如下：

```text
App 顯示語言        繁體中文（香港）
內容語言            繁體中文、English
翻譯內容為          繁體中文（香港）
內容地區            香港
```

- 用户可跳过；跳过后仍采用默认值。
- 用户选择“English”仅改变 UI 和可翻译内容的目标语言，不改变内容地区、配送国家或账户国家。
- 用户选择“東京”是更改“内容地区”，而不是把账户国家、时区、货币或配送地址改为日本。
- 登录完成后，将匿名偏好与账号偏好合并；若账号已有显式偏好，以账号值为准，并给出一次性说明。

### 4.4 既有用户迁移

| 旧值 | 迁移后值 |
|---|---|
| `zh-CN` / “简体中文” | `zh-Hans-CN` |
| `zh-TW` / “繁體中文”且用户地区为台湾 | `zh-Hant-TW` |
| “繁體中文”但无地区 | `zh-Hant-HK`，标记为系统迁移值，允许用户确认 |
| `en-*` | 保留可识别的 BCP 47 值；无地区时 `en` |
| `ja`、`ko` | 规范为 `ja-JP`、`ko-KR` |
| 旧 `countryCode` | 仅映射为账户国家/配送国家的已有事实，不改写 |
| 没有语言偏好 | 采用 `zh-Hant-HK` 默认值 |

迁移必须保存 `source: user | migration | default` 与更新时间。只有 `default` / `migration` 值可在后续首次确认提示中建议修改；显式用户选择永不被自动重置。

## 5. 语言范围、回退与文案语言

### 5.1 分批支持范围

| 阶段 | UI locale | 说明 |
|---|---|---|
| P0（默认） | `zh-Hant-HK`、`en` | 所有现有屏幕、弹层、错误/Toast、条款入口和交易状态必须完整可用 |
| P1 | `zh-Hans-CN`、`ja-JP`、`ko-KR` | 覆盖已在原型选择器中出现的语言；完成关键业务与客服文案本地化 |
| P2 | 其他 BCP 47 locale | 由市场准入、内容供给与合规优先级决定，不复制页面逻辑 |

`zh-Hant-HK` 是独立的首发文案，不应将简体中文机械转繁体后直接发布。香港术语、法律名称、货币写法和地址表达需要本地审校。台湾、澳门等繁体市场可复用共同键，但涉及地址、条款、营销、货币和敏感术语时须提供地区变体。

### 5.2 回退规则

1. 精确 locale：`zh-Hant-HK`；
2. 语言/文字共同资源：`zh-Hant`；
3. 产品基准语言：`en`；
4. 若键仍缺失，不展示 key、不混入开发占位符；记录可观测错误并使用经过审核的安全兜底文案。

法律条款、隐私政策、金融披露、费用规则、KYC/数字资产限制和配送规则**不得**通过语言回退跨市场替代。它们需按 `market + locale + version` 精确匹配；未提供有效文本时，隐藏受影响操作或提示“目前未能以你選擇的語言提供此服務”，并给出合规认可的版本入口。

### 5.3 香港繁体中文术语表（首发基线）

| 当前常见写法 | `zh-Hant-HK` 推荐写法 | 备注 |
|---|---|---|
| 首页 | 首頁 | Tab 文案 |
| 发现 | 探索 | 若品牌明确偏好“發現”，全产品统一，不混用 |
| 权益 | 會員權益 | 金融/会员域首选完整表达 |
| 我的 | 我的 | Tab 文案 |
| 设置 | 設定 | |

| 登录 / 登录方式 | 登入 / 登入方式 | |
| 手机号 | 手機號碼 | |
| 邮箱 | 電郵 | 可保留 Email 作为输入字段辅助词，但不可与“郵箱”混用 |
| 验证码 | 驗證碼 | |
| 通知 | 通知 | |

## 6. 信息架构与设置页面

现有“语言与地区”单页保留为入口，但字段应重新组织。建议展示为以下六项，全部显示当前值而非写死文本：

```text
語言與地區
├── App 顯示語言                 繁體中文（香港）
├── 翻譯內容為                   繁體中文（香港）
├── 內容語言                     繁體中文、English
├── 內容地區                     香港
├── 時區                         香港時間（Asia/Hong_Kong）
└── 顯示貨幣                     港元（HKD）
```

附加开关和说明：

- **自動翻譯內容**：默认开启；仅影响已支持的可翻译内容。关闭后优先显示原文，仍可在单条内容上手动翻译。
- **優先顯示本地內容**：高 / 中 / 低；只影响推荐排序，不隐藏其他地区内容。
- **使用裝置設定建議**：仅提示设备差异，不是持续强制同步。
- **管理語言資料**：说明删除某一语言包/离线资源的空间影响（如未来支持离线）。

账户国家、KYC 身份地区、配送地址、当前定位权限和个人主页所在地不放在此页直接修改：它们分别在账号、安全/合规、实体卡地址、系统权限和个人主页中管理，并清楚解释关系。

## 7. 静态界面文案设计

### 7.1 文案资源规则

所有用户可见的静态文案，包括标题、按钮、空状态、错误、Toast、确认弹窗、`placeholder`、`aria-label`、图片 `alt`、状态标签、筛选值和邮件/推送模板，都使用语义化 key 管理。组件不得直接拼接跨语言句子。

建议按产品域建目录：

```text
locales/
  zh-Hant-HK/
    common, navigation, auth, onboarding, feed, post, search
    social, profile, merchant, benefits, card, wallet, settings
    security, notifications, legal
  en/
  zh-Hans-CN/
  ja-JP/
  ko-KR/
```

key 以用途命名，不以中文或英文原句命名。例如：

```text
navigation.home
auth.continueWithProvider
post.translation.fromLanguage
post.comments.count
card.delivery.estimatedArrival
wallet.withdrawal.status.pending
```

变量采用 ICU MessageFormat 或等价能力处理插值、复数、选择与日期；禁止从多个翻译片段拼出一句话。

```text
post.comments.count =
  "{count, plural, =0 {暫未有留言} one {# 則留言} other {# 則留言}}"

post.translation.fromLanguage =
  "由{language}翻譯"

auth.welcomeBack =
  "歡迎回來，{name}"
```

数字、姓名、商家名和 URL 一律作为参数传入。参数不得预先格式化为某个语言的字符串；例如传入数值 `3800` 和币种 `JPY`，由格式化层决定输出。

### 7.2 不再使用“斜杠双语”作为常态

原型中如“配送至 / Deliver to”“继续 Continue”“申请办卡 Apply for Card”的写法，仅可作为尚未完成本地化时的设计占位。正式界面一次只显示用户选定的 UI 语言：

| 场景 | `zh-Hant-HK` | `en` |
|---|---|---|
| 主按钮 | 繼續 | Continue |
| 配送地址字段 | 配送至 | Deliver to |
| 申请实体卡 | 申請實體卡 | Apply for a physical card |
| 查看配送 | 查看配送追蹤 | Track delivery |

例外仅限不可翻译的法定名称、商家官方名称、短语教学场景或用户主动请求的双语内容。英文不应因“国际化”而混入繁体中文 UI。

### 7.3 视觉与可访问性要求

- 将当前偏简体中文的字体回退升级为覆盖繁体中文、日文、韩文及拉丁文的字体栈；设计和客户端均需验证缺字、标点、数字、emoji 和粗体表现。
- 所有按钮、列表项、筛选 chip、交易行和页头容器按最长翻译预留空间。英文、德文等可能比中文长 30%–60%；不通过缩小到不可读字体解决。
- 横向 chip 可以滚动；关键操作按钮不得仅依赖裁切或省略号。金额、订单号、地址和交易状态不可截断。
- 不以颜色或国旗单独表达语言/地区。国旗可作为国家选择器的辅助符号，必须同时有文本名称。
- 支持系统字体放大至 200%、屏幕阅读器和从右到左文本的基础安全渲染；即使首发不提供 RTL UI，也不得把用户名/URL/金额的双向文字顺序写死。
- 完成伪本地化测试，例如 `［Ťàşö — Ëxţëñďëď ！！！］`，以发现硬编码宽度、漏翻译 key 和字符串截断。

## 8. 内容、翻译与搜索

### 8.1 UGC 呈现规则

帖子、评论、私讯、昵称、话题、商家评价和用户上传的图片文字属于用户内容（UGC）。原则是“原文优先保真、译文可见可控、用户知道自己在看什么”。

建议将帖子数据从单一 `text` / `original` 方向明确为：

```text
Post
  id
  originalContent: { text, locale?, detectedLocale?, detectionConfidence }
  translations: [
    { locale, text, source: machine | human | author, status, createdAt }
  ]
  authorLocale?                 // 仅在用户允许时用于推荐，不作为公开身份
  placeId / merchantId
  createdAt                     // ISO 8601 instant
```

- `originalContent` 永远保存发布内容，不被翻译覆盖。
- 如果原文语言与 `translationLocale` 相同，直接显示原文，不出现“翻译自”行。
- 如果有可用译文且自动翻译开启，默认显示译文，并显示“由英文翻譯”与“顯示原文”；切换后显示“顯示翻譯”。
- 如果译文不可用，显示原文和“翻譯”操作；加载中、失败、受限内容应有不同状态，不可把失败误标为已翻译。
- 译文必须可反馈“翻譯不準確”，反馈附带源/目标 locale、模型/版本和内容 ID，不把私讯原文默认送往不必要的第三方服务。
- 用户可在发布前选择内容语言或使用自动检测确认。不会自动把机器译文当作用户原帖对外发表。
- 用户名、`@handle`、商户品牌、地点官方名、地址、金额和链接保持原样；仅描述性摘要可翻译。

现有 `PostText.vue` 中“翻译自{{ post.lang }}”及“显示原文/显示翻译”可作为交互雏形，但需接入上述明确的数据方向和本地化文案。

### 8.2 评论、私讯与通知

- 评论和私讯默认保持原文；自动翻译是每个用户自己的阅读偏好，不改变对方看到的内容。
- 私讯翻译首次使用需说明数据处理范围；敏感内容、未成年人保护和举报流程遵循隐私/安全策略。
- “我：”“今天”“昨天”“在线”“离线”“已读”等会随 UI locale 与用户时区格式化，不能存成中文字符串。
- 推送通知同时保存事件数据和可本地化模板 key；客户端或服务端在投递时按用户 locale 渲染。不要只保存已拼好的中文标题。

### 8.3 多语言搜索与发现

搜索不得只对当前显示译文做精确匹配。每个可搜索实体建议保存：

```text
SearchDocument
  entityType / entityId
  canonicalName                 // 官方/原始名称
  localizedNames[locale]
  aliases[]                     // 别名、旧名、常见写法
  transliterations[]            // 如 東京 / Tokyo / Dongjing
  originalText + translatedText // 内容检索字段，保留语言和来源
  region / geo / category
```

- 例如同一地点可被“香港”“Hong Kong”“香港島”“HongKong”检索到；“拉麵 / ramen / ラーメン”可命中同类实体。
- 搜索结果标题优先显示用户语言的本地化名称，同时保留官方原名作为次级信息，避免旅行场景中无法线下识别。
- Feed 的语言偏好是软排序信号：用户仍可看到高相关度的其他语言内容，并能按“原文 / 已翻譯”筛选。
- 地点和商家的地区名称由市场/locale catalog 格式化；不能在展示层把 `Hong Kong`、`香港`、`HK` 随意混用。

## 9. 数值、货币、日期、时区与地址

### 9.1 货币和金额

所有金额数据必须拆为数值与 ISO 4217 币种代码，禁止把 `US$10,000`、`¥3,800`、`HK$ 1,000` 当作业务字段或再从展示文本中解析。

```text
Money { amount: 1000.00, currency: "HKD" }
Money { amount: 3800, currency: "JPY" }
Money { amount: 10000, currency: "USD" }
```

显示层使用 `Intl.NumberFormat(resolvedLocale, { style: 'currency', currency })` 或各端等价 formatter。香港繁体中文验收示例：

| 数据 | `zh-Hant-HK` 显示 | `en` 显示 |
|---|---|---|
| `{1000, HKD}` | `HK$1,000.00` | `HK$1,000.00` |
| `{3800, JPY}` | `¥3,800` | `¥3,800` |
| `{10000, USD}` | `US$10,000.00` | `US$10,000.00` |

实际格式须以目标平台 `Intl` 结果为准，并在视觉 QA 中固定验收。交易原始币种始终可见；若提供 HKD 等值，仅作为辅信息，并显示“估算”、汇率来源和时间。手续费、税费、入账金额和总支付额均使用同一币种/换算标识，不跨币种静默相加。

### 9.2 日期、时间与相对时间

- 事件时刻、消息时间、订单创建时间存 ISO 8601 带时区/UTC instant；不要存预格式化 `2026-09-08 · 19:30` 文本。
- 仅代表自然日的业务字段（例如结算周期、法定到期日）可存 `LocalDate`，并明确其所属市场/时区。
- 渲染采用用户 `timeZone` 与有效 `uiLocale`。`zh-Hant-HK` 示例为 `2026年9月8日 19:30`；跨年、跨时区和夏令时必须正确。
- “剛剛 / 5 分鐘前 / 昨天 / 9月8日”由时间差与用户时区实时计算，不能把“今天”“昨天”作为数据写入聊天记录。
- 配送 ETA、活动截止和结算期同时说明所依据市场/承运商时区，避免用户跨境时误解日期。

### 9.3 地址、电话和国家名称

实体卡域继续沿用“国家配置决定字段、顺序、必填和校验”的方向，但本地化拆分为：

```text
CountryConfig
  code: ISO 3166-1 alpha-2
  localizedName[locale]
  addressSchema[market]          // 字段 key、顺序、required、input type、校验
  dialCode / phoneRule
  shippingAvailability
  shippingMethods
```

- 字段 key 保持语义化（`addressLine1`、`district`、`postalCode`），标签、帮助、错误、占位和示例从 locale 资源读取。
- 香港默认地址应使用香港字段顺序；不显示不适用的“邮政编码”必填项。英文香港地址和繁体中文香港地址可使用不同标签，但写入同一个结构化模型。
- 国家选择器按当前 UI language 显示本地化名称，支持英文原名/别名搜索；当前 `zh` / `en` 双字段不足以支撑扩展。
- 地址摘要不再固定取中文国家名，依 `uiLocale` 格式化；收件人填写的地址原文不可自动改写或机器翻译。
- 号码保存为 E.164 或“国家代码 + 号码”结构，显示时按 locale/市场格式化；输入规则仍以配送/认证国家决定。

## 10. 金融、会员卡与合规文案

金融和权益域比普通社交文案更严格。翻译设计应保留原始业务事实，避免因地区显示造成资质、费用或收益承诺错误。

1. 会员卡账户、钱包账户、实体卡办理费、提现、报销、分红、推广和数字资产的可用性由账户国家、KYC 状态、合作机构和市场准入共同决定，不由 UI locale 决定。
2. 所有费用、折扣、收益、预计送达和风险提示以数据/规则版本驱动；文字资源只负责表达。不能把“5–7 个工作日”“95 折”“0.05%/日”等写死在翻译文件或页面中。
3. 每份条款、隐私政策、费用披露、卡服务协议和推广规则保存语言版本、适用市场、生效时间、版本号与同意记录。用户切换语言后，可阅读译文，但法律效力版本和缺失语言提示需经法务确认。
4. 卡片、KYC、提现、数字资产等受限功能需采用明确本地化状态：可用、需验证、所在地区暂不可用、服务维护、需联系客服；不以泛化的“失败”替代合规原因。
5. 商家优惠的有效期、税费、币种、核销地点与限制条件使用结构化数据。翻译后的营销短文不得改变折扣条件或适用范围。

## 11. 数据与状态设计

### 11.1 偏好模型

建议新增独立的 `LocalizationPreferences`，而不是继续仅在 `AuthUser.language` 或各页面局部状态中保存：

```ts
interface LocalizationPreferences {
  uiLocale: string                 // zh-Hant-HK
  translationLocale: string        // zh-Hant-HK
  contentLocales: string[]         // ['zh-Hant', 'en']
  contentRegion: { country: string; cityId?: string }
  timeZone: string                 // Asia/Hong_Kong
  displayCurrency: string          // HKD
  autoTranslate: boolean
  localContentPriority: 'high' | 'medium' | 'low'
  sources: Partial<Record<keyof LocalizationPreferences, 'user' | 'migration' | 'default' | 'channel'>>
  updatedAt: string
}
```

账号中保留 `accountCountry`、公开所在地及合规状态；它们不应复用 `contentRegion`。匿名偏好可先写入本地存储，登录后通过明确的合并规则同步至账户。对于跨端产品，服务端账户偏好是最终来源，本地仅作启动缓存与离线容错。

### 11.2 资源与配置模型

| 资源类别 | 需要本地化 | 不能仅做翻译的原因 |
|---|---|---|
| UI 文案 | 是 | 语言、复数、占位、无障碍文本不同 |
| 国家/地区名 | 是 | 显示名称、别名和排序语言不同 |
| 商家/地点 | 是，保留原名 | 旅行者需识别官方原名与本地名 |
| 地址字段 | 是，且按市场配置 | 不同国家字段、顺序和校验不同 |
| 交易/权益规则 | 是，且版本化 | 费用、限制和法律文本不能只换语言 |
| 帖子/评论/私讯 | 可翻译，保留原文 | UGC 所有权、准确性和隐私要求不同 |
| 图片/视频 | 视资产而定 | 含文字的创意、OCR、字幕和替代文本需单独处理 |
| 图标/日期/金额 | 通过格式化与 a11y 描述 | 不是单纯文案资源 |

### 11.3 资源交付与质量门禁

- 文案 key、英文基准、`zh-Hant-HK` 审核稿和上下文截图进入翻译管理流程；不直接复制组件源码给译者。
- 资源变更需 lint：缺 key、未使用 key、参数名不一致、HTML/富文本不安全、ICU 语法错误均阻断合并。
- 每个 locale 的完成度按产品域统计。金融、认证、删除账号、报错、空状态和辅助文本没有达到 100% 时，不可标记为该语言“已支持”。
- 翻译内容、机器译文和人工审校内容分别标记来源与版本，支持回滚和问题追踪。

## 14. 验收标准与测试矩阵

### 14.1 必须通过的核心场景

1. 清除本地偏好后首次启动，首屏、Tab、弹窗、输入提示和辅助文本均为 `zh-Hant-HK`；内容地区为香港，翻译目标为繁体中文（香港）。
2. 将 UI 切为 English 后，所有静态 UI（包括错误、Toast、`aria-label`、空状态）切为英文；内容地区仍为香港，账户国家和地址不改变。
3. 将内容地区切为东京后，UI 仍为繁体中文（香港），时区和配送地址不自动改变。
4. 一篇英文原帖在繁体香港默认下显示已批准的繁中译文、“由英文翻譯”和“顯示原文”；关闭自动翻译后显示英文原文，手动翻译仍可用。
5. 帖子没有可用译文时，绝不把原文错误地标为翻译；翻译失败有可恢复提示。
6. 切换语言后，`HKD`、`USD`、`JPY` 的原始币种和金额不变；不出现 `US$` 与 `HK$` 静默相加或汇率未标识的换算。
7. 同一 UTC 消息在 `Asia/Hong_Kong` 与 `Asia/Tokyo` 下显示正确本地时间；跨日“昨天/今天”正确。
8. 新建实体卡地址草稿默认香港，香港字段不强制邮递区号；改选日本或美国后字段顺序、标签、校验和国家名与 UI language 一致。
9. “香港 / Hong Kong / HK”、商家原名和罗马字别名可检索；结果同时帮助用户识别官方原名。
10. 字体放大 200%、最长英语文本、日语/韩语文本、长商户名、金额/订单号、屏幕阅读器和伪本地化下均无关键操作截断。

### 14.2 发布前测试维度

| 维度 | 最低覆盖 |
|---|---|
| UI locale | `zh-Hant-HK`、`en` 全量；P1 五种 locale 全量 |
| 身份状态 | 未登录、首次注册、已有账户、匿名偏好合并、迁移用户 |
| 内容状态 | 同语言原文、有机器译文、有人工译文、无译文、翻译失败、关闭自动翻译 |
| 市场/地址 | HK、JP、US、不可配送国家；不同电话/邮编规则 |
| 金融状态 | USD/HKD/JPY、费用、优惠、待处理/失败/完成、地区受限 |
| 时间 | 跨日、跨年、跨时区、夏令时、自然日结算周期 |
| 质量 | key 完整率、伪本地化、视觉回归、无障碍、截图人工审校 |

建议监控指标：语言切换成功率、缺失翻译 key 数、翻译失败率、译文切回原文比例、语言相关客服工单、按语言的注册/发布/卡申请转化，以及地区受限功能的误触发率。

### 17.2 架构与代码落点（对照 §3、§4、§7、§11）

| 设计条款 | 实现情况 |
|---|---|
| §3 偏好解耦模型 | `src/i18n/index.ts` `LocalizationPreferences`：原型收敛为 `uiLocale` / `contentRegion`（global/country/city 三级）/ `autoTranslate` + `timeZone` / `displayCurrency`（保留为格式化基础配置，不在设置页暴露）；译文目标固定跟随界面语言；持久化 `localStorage.taso-locale`，账号快照存 `AuthUser.prefs` 登录合并（§4.3） |
| §4.1 默认值 | 原型采用「设备建议冷启动」（全球化评审落地）：默认表 `DEFAULT_PREFS` 为 en/全球/UTC/USD 纯回退；首启实际取 `suggestPrefs()`——设备语言 → 已收录 UI 语言映射（含新五语言）、设备时区 → `TZ_CITY` 城市（新增巴黎/河内/胡志明市/莫斯科/利雅得）、未覆盖回退全球。香港不再作为全球默认（评审修订） |
| §4.2 生效优先级 | 会话显式保存 > 账号已存偏好 > 设备建议；显式选择标记 `source: 'user'` 永不自动重置 |
| §4.4 旧值迁移 | `MIGRATE_LANG`：zh-CN/zh/zh-Hans→zh-Hans-CN、zh-TW/zh-Hant→繁体系、ja→ja-JP、ko→ko-KR，V2.8 新增 fr→fr-FR、vi→vi-VN、th→th-TH、ar→ar-SA、ru→ru-RU |
| §5.2 回退规则 | `t()` 回退链：精确 locale → 语言/文字（zh-Hant-HK→zh-Hant；CATALOGS 同时注册 `fr-FR` 与裸 `fr` 别名）→ en 基准；缺失 key 记录控制台警告并回落英文安全文案 |
| §7.1 文案资源 | 单层语义化 key 目录 `src/i18n/locales/*.ts`（10 份）；`t(key, params)` 支持 `{var}` 插值与 ICU-lite 复数 `{n, plural, ...}`；品牌名/handle/商户官方名/币种代码不翻译 |
| §7.2 去斜杠双语 | 全站文案走 `t()`；本轮顺带修复欢迎页标题残留硬编码「Welcome to Taso」→ 新增 `welcome.heading` key（十语言），其余屏幕经扫描无硬编码用户可见文案残留 |
| §7.3 视觉与无障碍 | 字体栈含繁/日/韩回退（V2.0）；金色 AA 墨色（V2.4）；`aria-label` 全部走 `t()`（V2.0）；RTL 见 §17.4 |
| §8.1 UGC 呈现 | `Post = original{text, locale} + translations[]{locale, source}`，原文不可变；呈现规则在 `i18n/content.ts postView()`：同语言直显原文不出「由 X 翻譯」行、自动翻译开且译文可用才默认显示译文、无译文显示原文 + 「翻譯」按钮且绝不误标为已翻译；「报告译文问题」反馈入口已有 |
| §8.3 搜索 | `SEARCH_DB` SearchDocument：canonical + localizedNames + aliases（如 東京/Tokyo/渋谷/라멘 互检）；V2.8 补齐全部实体的十语言名称 |
| §9 数值/日期/地址 | `Money{amount, currency}` + `Intl.NumberFormat`（`fmtMoney`，裸符号 `$`/`¥` 无歧义化为 US$/HK$/JP¥）；时刻存 ISO instant 按用户时区渲染；自然日存 YYYY-MM-DD（`fmtLocalDate*` 已加容错，见 §17.5）；`fmtMoneyEstimate` 等值换算自带「估算·汇率·时间」披露；实体卡地址字段按国家配置 + labelKey 本地化（V1.8/V2.0） |

### 17.3 运营版扩展内容

- **地区目录**：`REGIONS` 扩为 17 个城市 × 十语言名称（新增巴黎、河内、胡志明市、莫斯科、利雅得，别名含 Saigon/Moskva 等）；时区→城市建议表、国家→展示货币映射（FR→EUR、VN→VND、RU→RUB、SA/AE→SAR/AED）、演示汇率（VND/RUB/SAR/AED）与货币清单同步扩展。
- **种子数据**：三个旗舰帖（焼肉/手冲咖啡/빙수）补齐全部 10 种 UI 语言的演示译文（标记 `source: 'machine'`，对应 §8.1 机器译文态）；其余帖子保持原文——这是有意的对照态，用于演示「无可用译文」分支（显示原文 + 翻译按钮，不假装已翻译）。7 位演示成员简介与 9 个搜索实体名补齐十语言。
- **新语言的质量校验**：脚本核验三件套——十目录 key 与 en 奇偶对齐、`{param}` 占位符集合与 en 一致、逐语言脚本字符混入检测（如法文值中不得出现西里尔/泰文，俄文值中不得残留 CJK 等；品牌词与搜索占位提示除外）。

### 17.4 阿拉伯文 RTL 支持边界

已实现（§7.3「基础安全渲染」口径）：

- `<html dir="rtl" lang="ar-SA">` 随界面语言自动切换（`isRtlLocale()` + persist 钩子）；
- 弹性布局随文档方向自动镜像；CSS 中以物理属性书写的对齐与装饰（列表对齐、开关旋钮、角标、返回箭头图标）有 `html[dir="rtl"]` 覆盖块做基础镜像；
- 浏览器实测：欢迎页、登录页、首页信息流在阿语下整体右起镜像，阿语机翻译 + 「عرض الأصل / عرض الترجمة」切换、金额与相对时间本地化均正确；用户名/商户名等双向文本混排由浏览器 bidi 处理。

**未做**：完整 RTL 视觉审计（图标方向语义、图表时间轴、滑动交互方向、伪本地化测试）；数字/金额在阿语下的阿拉伯-印度数字呈现依赖 Intl 默认行为，未做产品级验收。该项与 §14.2 的 RTL 维度仍是发布前待办。

### 17.5 本轮顺带修复的既有缺陷

1. **欢迎页硬编码英文标题**（违反 §7.2/P0 完成标准）：`ScreenWelcome.vue` 的「Welcome to Taso」改为 `welcome.heading` key。
2. **`fmtLocalDate*` 健壮性**：原实现对入参硬拼 `T00:00:00Z`，一旦传入完整 ISO 时间戳会生成 Invalid Date，`Intl.format` 抛 RangeError 并在无错误边界的情况下炸掉整棵组件树（浏览器走查注入演示账号时复现整页空白）。已改为：完整 ISO 按时刻解析、无效输入原样返回。真实注册流只存 YYYY-MM-DD，此前用户不可触发，但十语言验收阶段会更易踩中。
3. **`isRtlLocale` 声明位置**：曾误置于 persist 块之后导致模块初始化 TDZ（与 V2.4 修复过的 REGIONS 陷阱同款），已移至 persist 之前并留注释。
